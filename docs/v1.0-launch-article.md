# InkForge v1.0：一个用 Rust 写的博客平台，和它背后的 500 次编译

> 我花了一年多时间，用 Rust 从零写了一个博客系统。没有状态管理框架之争，没有微服务拆分的烦恼，只有一个二进制文件，丢到服务器上就能跑。这篇文章聊聊选了哪些技术、踩了哪些坑、以及为什么这件事值得做。

---

## 为什么要造轮子

市面上不缺博客系统。WordPress 占了全球 40% 以上的网站，Ghost、Hugo、Hexo 各有各的拥趸。但它们都有一个共同点——要么太重，要么太远。

WordPress 是一艘航母。装完以后，你要操心 PHP 版本、MySQL 调优、插件安全漏洞、缓存层配置。Ghost 虽然是 Node.js 单体，但依赖树深不见底，`node_modules` 的体积比你的博客内容还大。静态站点生成器如 Hugo 很快，但你得在本地编译完再推到服务器，改个错别字也要走一遍 CI。

我想要的东西很简单：**一个二进制文件，跑起来就是完整的博客平台**。不用装数据库、配 Nginx 反代也很简单，几行配置就搞定、不用理解 Docker 网络。Rust 的零依赖单二进制部署正好是这个问题的完美答案。

还有一个说不出口的理由：**掌控感**。自己的博客平台，每一行代码都知道在做什么。出了问题不翻别人的 issue tracker，直接打断点进去看。数据在自己手上，想导出什么格式就写个函数。这种感觉，懂的人都懂。

一个人写，没 deadline，没产品经理。想停就停，想重构就重构。这个项目前前后后写了一年多，推倒重来过两次——第一次是用 Actix Web + Askama，第二次就是现在的 Axum + MiniJinja。每次推翻都更接近心里那个"对的"设计。

## 技术选型

### 后端：Axum + SQLite + MiniJinja

**Axum** 是 Rust 生态里最成熟的 Web 框架之一，由 Tokio 团队维护，类型安全的 extractor 设计深得我心。路由是从 `Router` 链式构建，中间件用 `tower`，错误处理用 `IntoResponse`，整个体系很一致。

**SQLite 而不是 PostgreSQL**——这是最常被问到的问题。我的回答很简单：够用。个人博客撑死了几千篇文章、几万条评论，SQLite 的并发和性能完全可以胜任。而且 SQLite 是文件级数据库，备份就是一个 `VACUUM INTO` 命令的事，恢复就是把文件覆盖回去。零运维，不用起一个 `postgres` 服务，不用管理连接池上限。加上 FTS5 全文索引，搜索也不含糊。

**MiniJinja 而不是 Askama**。第一版用的 Askama，编译时模板——类型安全、零运行时开销，听起来很 Rust。但很快发现编译时模板的限制：主题系统没法做。Askama 的模板在编译期就确定了，用户上传一个 ZIP 包，里面的 `.html` 模板怎么加载？MiniJinja 是运行时模板引擎，支持动态 loader、自定义函数和 filter，完美契合"用户可切换主题"的需求。代价是模板错误要运行时才能捕获，但这个取舍很值。

还有一个安全细节：模板 loader 里加了路径穿越防护。`canonicalize` 后检查是否在主题目录内，防止通过 `../../etc/passwd` 这样的路径读到系统文件。

### 前端：React + Tiptap + CodeMirror

前端选型是争议最少的部分。React 19 + TypeScript + Vite 8 + Tailwind CSS v4，标准的 2024-2025 前端技术栈。

编辑器选 Tiptap，基于 ProseMirror，开箱即用的富文本编辑体验，支持 Markdown 快捷键、图片拖拽、代码块高亮。源码模式用 CodeMirror 6，双向同步——在 Tiptap 里改一个字，切到 CodeMirror 能看到对应的 Markdown 源码更新，反之亦然。这个同步逻辑是前端最复杂的部分，后面会说到踩的坑。

为什么不用 Leptos 或 Dioxus？这两个 Rust 前端框架在 2024 年初还不够成熟，组件生态、开发工具链和 React 差距很大。对于管理后台这种需要大量交互的页面，用成熟的 React 生态开发效率高得多。前后端分离不是什么坏事，Axum 负责 API 和模板渲染，React 只管后台 UI，职责清晰。

CSS 方面选 Tailwind CSS v4，橙色调的玻璃拟态风格。v4 的配置方式从 JS 变成了纯 CSS，`@import "tailwindcss"` 就行，清爽很多。

## 核心功能走一遍

### 安装向导

把二进制丢到服务器上，`./inkforge` 启动，浏览器打开就是安装向导。填写站点信息和创建管理员账户，点确认就完成。安装状态用 `setup_stage` 状态机管理，没完成安装前前台自动引导到安装页。

### 双模式编辑器：所见即所得 + 纯源码

这是管理后台最核心的组件。Tiptap 提供完整的富文本编辑能力——标题、加粗、斜体、链接、图片、代码块、列表、引用、分割线。颜色和高亮用 `@tiptap/extension-color` 和 `@tiptap/extension-highlight`，支持文本颜色和背景色。

一个独立的 CodeMirror 面板，实时展示 Markdown 源码。两边切换通过按钮点击，切换到 CodeMirror 时从 Tiptap 的 ProseMirror 文档导出 Markdown，切换回来时解析 Markdown 重建文档。

双向同步的核心是 `tiptap-markdown` 这个库，在 Tiptap 的 `onUpdate` 回调里实时生成 Markdown 字符串，存到 React state。CodeMirror 的 `onChange` 回调同步更新另一个方向的 state。这里状态管理稍有不慎就会死循环——编辑器 A 更新触发 B 更新，B 更新又触发 A 更新。解决的方案是用一个 `isProgrammaticChange` 标记位：代码内部触发的更新跳过回调，只有用户操作才传递变更。

### 主题系统：ZIP 上传即生效

主题打包成 ZIP 文件，里面包含 `theme.toml` 配置文件和 `templates/` 模板目录。上传后自动解压到 `themes/` 目录，MiniJinja 的动态 loader 实时加载。

模板的 `Environment` 做了缓存优化。每请求只 clone 一份缓存的 base Environment（loader + 静态 filter + `theme_assets_url` 函数），然后注入请求相关的全局变量和插件扩展。避免了每次请求重新构建 loader，但保留了请求级数据的隔离。

`tojson_script` 这个自定义 filter 是我比较喜欢的小细节——它把数据转成 JSON 后，把 `<`、`>`、`&` 和 Unicode 行分隔符转义掉，安全地嵌入 `<script>` 标签。模板里写 `{{ post|tojson_script }}` 就行，不用手写 `JSON.parse` 的安全处理。

### 评论 + WebSocket 实时推送

评论系统本身不复杂：游客在前台提交，管理员在后台审核。但我想加一个功能——新评论来了，管理后台能看到实时通知。

实现比预想的简单很多。Rust 端用 `tokio::sync::broadcast` channel，容量 256。评论创建/审核/删除时往 channel 发 `ServerEvent`（一个 enum，tag 式 JSON 序列化）。管理后台的 WebSocket 连接走 JWT 认证的 `upgrade`，前台的连接按 `post_id` 过滤、只推送该文章审核通过的评论。

没有用 Redis Pub/Sub，没有引入消息队列。一个 `broadcast::channel` 搞定。对于单体应用，这就够了。等哪天要水平扩展再说。

### 备份恢复：定时调度 + 一键还原

备份是用 SQLite 的 `VACUUM INTO` 命令生成一致性快照——先 `WAL checkpoint(FULL)` 把 WAL 写入主文件，再 `VACUUM INTO` 到临时文件。这个方式比直接 `Copy` 数据库文件可靠得多，不会拷到不完整的事务状态。

然后和 `uploads/media/` 目录的文件一起打包成 ZIP，计算 SHA256 hash 写入 `manifest.json`。恢复时要过三道关卡：hash 校验 → `PRAGMA integrity_check` 验证 → 文件替换（最多重试 5 次，失败则用逻辑逐表恢复 fallback）。

定时调度用 `tokio-cron-scheduler`，支持 daily/weekly/monthly，可以配置执行时间。调度器的生命周期用了一个"不太 Rust"的做法——`std::mem::forget(scheduler)` 防止 scheduler 被 drop 后 job 停止。这是因为 scheduler 在 `start()` 后需要持续存活，但函数退出时会被自动 drop。`forget` 泄漏它，让它在后台一直跑。

## 插件系统演进

插件系统不是一开始就设计好的，是一步步长出来的。

### 第一阶段：Plugin trait

最初只有一个 `Plugin` trait，四个方法：

```rust
#[async_trait]
pub trait Plugin: Send + Sync {
    fn name(&self) -> &str;
    fn version(&self) -> &str;
    async fn init(&self, _state: &Arc<AppState>) -> AppResult<()>;
    async fn shutdown(&self) -> AppResult<()>;
}
```

已经够用——插件加载、初始化、关闭，生命周期完整。把插件代码放在 `plugins/` 目录下，手写一个 register 函数把它们注入。

### 第二阶段：自动发现

手写注册太烦了，每次新加插件要改代码。于是把注册逻辑搬到了 `build.rs`：编译时扫描 `plugins/` 目录，找到 `plugin.toml` + `lib.rs` 成对存在的子目录，自动生成 `register_all()` 函数。插件开发者只需要创建目录、写 manifest 和 lib，编译时自动接入。

### 第三阶段：Hooks 系统

插件不光要有自己的路由，还要能介入系统的核心流程。于是设计了 Filter / Action 两种 Hook：

- **Filter**：可以修改数据。比如在文章保存前注入关键词、修改 slug。
- **Action**：只做副作用。比如文章发布后发 Webhook 通知、记录日志。

Hook 的定义在 `HookData` 枚举里——`PostBeforeSave`、`PostAfterPublish`、`PostBeforeRender`、`CommentBeforeCreate` 等。示例插件里有一个 `post.after_publish` Action，每次文章发布打一条 tracing 日志。

### 第四阶段：配置面板 + 前端插槽

插件不应该只是后端代码。`plugin.toml` 里加了 `[[settings]]` 段，定义配置项的 key、label、type、default，后台自动渲染设置表单。存储用 `plugin_settings` 表，`ON CONFLICT` upsert。

前端方面，插件可以声明 `[[slots]]`——定义插槽的 target（比如 `post-editor`、`sidebar`、`dashboard`），管理后台用 React Context 分发 slot 列表，在对应位置渲染 `SlotContainer` 组件。插件的 admin UI 存储在 `plugins/` 目录的静态子目录里，通过 `/static/plugins/` 路由暴露。

从 trait 到 hooks 到 settings 到 slots，四个阶段的演进每一步都是实际需求驱动的——没有为了"大而全"而过度设计。

## 踩过的坑

### 坑一：编辑器颜色在文章页不显示

这个问题让我 debug 了三轮，每一次都觉得自己"找到了根因"，结果都不对。

Tiptap 编辑器里设置了文本颜色，后台预览正常，保存后的文章页面颜色消失。第一反应是 MiniJinja 模板渲染问题——检查 `{{ content | safe }}` 是否正确输出了 `<span style="color: red">`。输出了，那问题在 HTML sanitizer。

第二反应是 `ammonia` 的配置问题。`ammonia` 是 Rust 的 HTML 净化库，默认会去掉 `style` 属性。我写了一个 `sanitize_html` 函数，用 `ammonia::Builder` 配置了 `span` 和 `mark` 标签的 `style` 属性白名单。代码看起来没问题，编译也通过。但颜色还是不显示。

排查了两轮——检查 MiniJinja 模板渲染、检查数据库是否正确存储——都没找到问题。第三轮才注意到函数最后一行：`ammonia::clean(html)`。不是 `builder.clean(html)`。我配置了 builder，但实际调用的是 ammonia 的全局默认函数——它不认识我加的白名单，`style` 属性被静默丢弃了。

教训：一个字母的差别——`ammonia::clean` 和 `builder.clean`——花了三小时。所有的"为什么明明配对了却不生效"，都值得去查一下你实际调的是不是你以为的那个函数。

### 坑二：TanStack Query 缓存导致保存后内容空白

用 React Query 做文章列表的数据管理：`useQuery` 拉列表，`useMutation` 提交编辑。编辑完调 `invalidateQueries` 刷新列表——这套逻辑看起来天衣无缝。

但有一个场景出问题了：在文章列表页点编辑，修改后保存，回到列表页发现刚才修改的文章标题变成空白。查了半天发现是 `staleTime` 的副效应。

我给文章详情 query 设了一个比较大的 `staleTime`（5 分钟），觉得一篇文章短时间内不会频繁修改。但保存是 `POST` 操作，`onSuccess` 回调里 invalidate 了列表 query，没 invalidate 详情 query。回到列表页后，React Query 从缓存拿详情数据——因为 staleTime 没过，它认为缓存还是新鲜的，但实际服务器数据已经变了。列表渲染时取了 detail 缓存里的标题字段，显示空白。

教训：`staleTime` 是个反模式触发器。它的设计意图是"在时间内不重新请求"，但在 mutation 场景下，必须精确 invalidate 所有相关 query。最终把所有 mutation 的 `onSuccess` 改成 `queryClient.invalidateQueries()` 不带参数——全部刷新，简单粗暴但不出错。性能损失对一个管理后台来说可以忽略。

### 坑三：自研 SWR 缓存的竞态条件

早期前端数据请求是自己写的：一个全局 Map 存 `{key: {data, timestamp, promise}}`，用 `stale-while-revalidate` 策略。stale 时先返回缓存，再发请求更新。

看起来和 React Query 差不多，但有一个致命 bug：**竞态条件**。

用户快速切换文章分类：点"技术"→ 立即点"生活"→ 立即点"随笔"。三个请求几乎同时发出。服务器响应顺序和请求顺序不一致——"随笔"先返回，"技术"后返回。最后 Map 里存的是"技术"的旧数据，但用户已经切到"随笔"分类了。

React Query 处理这个问题的方案是 `queryKey` + `AbortController`。每次新请求触发时，前一个同 key 的请求被 abort，响应被丢弃。自己实现这个逻辑涉及到锁定、版本号、请求取消，越写越复杂。最终一刀切——删掉自研缓存，全面迁移 React Query。

教训：缓存不是你想象的那样简单。SWR 策略看起来只有几行代码，但边角 case 的数量会让你怀疑人生。React Query 在这个领域投入了几年打磨，不要用周末的项目去替代它。

## 性能数据

在 1 核 2G 的云服务器（Digital Ocean）上，InkForge 的表现：

| 指标 | 数值 |
|---|---|
| 冷启动时间 | < 1 秒 |
| 页面 TTFB | < 50ms（本地）/ ~80ms（远端） |
| 内存占用 | ~30MB（稳定运行） |
| 二进制大小 | ~11MB（release + LTO + strip） |
| SQLite 查询延迟 | < 1ms（单表百级数据） |

几个关键的编译优化：`lto = true` 启用链接时优化，`opt-level = "s"` 优化体积，`codegen-units = 1` 单代码生成单元让编译器有更大的优化空间，`strip = true` 剥离符号表。这些配置加起来，release 编译时间大约 3-5 分钟（取决于 CPU），但产物的体积和性能都值得等待。

管理后台的构建产物放在 `src/admin/dist/` 目录下，后端通过 Axum 的静态文件服务直接读取。开发时前端走 Vite 开发服务器（端口 5173），API 代理到后端（端口 2000），热更新秒级。

## 下一步

v1.0 是一个坚实的起点，但不是终点。接下来几个大方向：

### WASM 插件运行时

现在的插件需要编译进二进制——要装插件就得重新编译。这个体验太差了。计划引入 WASM 运行时（wasmtime 或 wasmer），让插件编译成 `.wasm` 文件，上传即用。沙箱隔离、热加载、远程安装——这些能力需要 WASM 的 `component model` 或至少一个稳定的 ABI 定义。

### SSG 静态站点生成

InkForge 已经有了完整的模板引擎和内容管理，但渲染是服务端动态的。加一个 SSG 模式——在管理后台点"发布站点"，把所有页面渲染成静态 HTML，输出到一个目录。配合 GitHub Pages 或 OSS 直接托管，适合对性能和成本有极致要求的场景。

### Tauri 桌面打包

项目里已经集成了 Tauri 2 的单进程启动模型（`src-tauri/`），但还没走完打包验收闭环。目标是：双击图标启动，自动打开系统浏览器访问本地端口，关闭窗口后后台服务自动退出。让非技术用户也能"装一个软件就能写博客"。
